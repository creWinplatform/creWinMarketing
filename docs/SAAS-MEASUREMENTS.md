# Phase 4 - source-linked automatic measurements

## Scope and reuse

Standard SaaS projects now map existing goal stages to existing GA4, Search
Console or signed product-event connections. This extends the modular monolith,
existing encrypted credential registry, goal definitions, `platform_jobs`, private
worker, audit log, metric table, report screen and CSV export. Crewin's legacy
analytics, ABP connector, goals and credentials are not migrated or reused.

Manual observations remain manual. Automatic readings do not enter the manual
dashboard funnel or get added to manual values. One automatic mapping per goal
stage avoids parallel definitions. Changing configuration versions it and fences
in-flight reads; old observations and job provenance remain attributable.

## Available measurements

- GA4: eventCount, keyEvents, totalUsers and sessions. Optional exact eventName
  filter only for eventCount/keyEvents. Single aggregate over the requested
  period; unique users are never summed across daily rows. Property timezone is
  taken from the provider. Thresholding, other-row data loss or sampling gives
  partial status with no numeric observation. No rows means no data, not zero.
- Search Console: finalized web clicks/impressions, grouped by date at property
  level, in America/Los_Angeles. At most 31 days. Missing days are conservatively
  partial because omitted rows do not establish zero traffic. No index status,
  ranking or PageSpeed values are inferred from these counts.
- Product events: event count or distinct observed entity count for one source,
  immutable source version and declared event name. Existing event IDs deduplicate
  ingestion; this reader counts stored received events as of its query timestamp.
  Only an active source with uninterrupted local coverage for the full retained
  UTC period may produce a value, including a genuine observed zero. Upstream
  instrumentation completeness is not independently verified. These are observed
  events, not a guarantee of every real business action.

Numbers, event names and metric fields are never generated by AI. No provider
key, raw event attributes, contact identity or provider error payload is returned.
The report does not combine sources, compute cross-source conversion rates or
claim causal campaign attribution. Those require a separate identity/attribution
contract and adequate evidence.

## Operation

In Analytics > Automatic measurements, select a goal/stage, existing source,
metric and optional event. Daily synchronization is explicitly opt-in. Choose a
closed 1-31-day range within the last 90 days; source retention can be shorter.
Each result shows its date range, source/resource, timezone, check time and state.
Results older than 24 hours or invalidated by access/configuration changes are
not labelled current. Missing, partial and failed are not rendered as zero.

Default and daily scheduled range: seven calendar dates ending three UTC calendar
days ago, to allow for Google processing delay. Each provider interprets those
calendar dates in its documented timezone, which is shown; they are not identical
UTC intervals and must not be merged. A different period can be queried manually.

`Sync now` durably enqueues, then runs a read through the existing queue. Polling
is bounded to active work. Active jobs remain inspectable/cancellable even while
the user selects another date range. Configuration edits/pause cancel pending
work; late replies cannot overwrite cancellation. A read-only expired lease can
recover up to three times without duplicate canonical observations.

Pausing only stops future work: a compatible successful observation remains
visible with its original check time. Changes to the goal, metric, event or
source do not reuse an incompatible observation. Optimistic configuration
versions still advance on pause and stale pending writes remain fenced.
A new manual read defers daily eligibility by 24 hours; an idempotent replay
does not move the schedule. An overdue mapping displays waiting for scheduler,
not a promise that a background worker is running.

Daily work requires the EXISTING private worker or authenticated cron to run:

```powershell
npm run worker:platform
```

Configure CRON_SECRET and PLATFORM_WORKER_ORIGIN as documented previously. Saving
a daily mapping does not install a system scheduler. This implementation does
not start a worker, deploy, grant Google access or enable email/social publishing.
The worker considers at most two due mappings and processes at most three queued
jobs per invocation, with an elapsed-time budget. Next-sync timestamps are queue
eligibility times, not guaranteed completion times.

## API and permissions

- `/api/platform/measurements`: GET workspace, optional `from`/`to`, or `id` for
  one scoped job. Project readers can inspect aggregates; viewer source selectors
  are empty and `canManage` is false.
- POST `action:save`: goalId, stageIndex, connectionId, metric, eventName, enabled,
  expectedVersion (0 for new stage). Provider, source version, owner/scope and goal
  signature are resolved server-side. Connection managers only.
- POST `action:enqueue`: bindingId, expectedVersion, from, to, idempotencyKey.
  A replay returns the same job; another range/version cannot reuse that key.
- POST `action:run` or `action:cancel`: id. Initiator, mapping manager and manual
  runner authority are checked before and after network waits.
- POST `action:pause`: id, expectedVersion. Works even after source revocation.
  Lost manager authority disables daily mappings; restoring a role does not
  silently re-enable them.
- Existing `/api/platform/operations?resource=export&mode=automatic&from=...&to=...`
  exports source/period/status-labelled CSV with formula escaping. Existing manual
  export stays unchanged. Manual write/delete APIs cannot overwrite automatic rows.

All authenticated writes require same-origin requests and bounded JSON. Google
requests use fixed official hosts, no redirects, scoped saved credentials and
bounded time/response size. Refresh is compare-and-swap under the current lease;
it cannot overwrite a concurrent credential rotation or revive a revoked grant.

## Storage and limits

Migration 19 adds scoped versioned mappings and per-job result/provenance metadata,
and extends the EXISTING metric table. A canonical automatic observation is unique
by project, binding version and date range. Re-reading updates that observation,
while prior job results retain their original value/check time. No manual rows or
SES/rehearsal records are rewritten. Migrations are repeatable and transactional.
Each new job snapshots its public source name and resource. A connection rename
or property change cannot relabel an earlier result or its CSV as a new property.

Pilot limits: 20 mappings/project; 100 new reads/project/UTC day; 500 retained
measurement jobs; 2,000 canonical automatic observations. Limits fail explicitly,
not via silent truncation/deletion. Manual limits remain independent. Production
retention/export policy and broader billing quotas remain later launch work.

Google setup reuses existing project OAuth with analytics.readonly or
webmasters.readonly. Enable Analytics Data API in addition to the existing Admin
API for GA4 reports. No legacy environment service-account fallback exists.
Live OAuth consent/provider acceptance cannot be substituted with unit fixtures.

## Visits from posts: tagged own-site links (schema 57, 27 October 2026)

Approved social posts that link to the project's own site now say which post a visit came from.

**Tagging (in the preview, before approval).**
- Links to the project website (and its subdomains) get `utm_source=<channel>`, `utm_medium=social` and `utm_campaign=rz_<10 hex>`.
  - The channel is `linkedin`, `facebook`, `x` or `telegram`.
  - The campaign value is one project-scoped hash per saved content item or campaign, so it reveals no id.
- Some links are never changed:
  - links to other sites;
  - links that already carry any `utm_` parameter;
  - links with credentials;
  - Instagram captions, whose links are not clickable.
- The tagged text is what the preview shows, what is approved, what is stored in the encrypted snapshot and what is sent. The preview says how many links were tagged.
- Tagging is on by default and can be switched off by an owner/admin (`connections.manage`).
- Switching it changes the source digest. A post approved under the other setting must be reviewed again; a queued one is blocked as `changed`.

**Results (Google Analytics).**
- An owner/admin chooses one of the project's active GA4 connections in "Visits from your posts" on the publishing page.
- It is then read once a day by the worker, as that person, with a manual refresh at most every 10 minutes and 24 reads a day.
- One `runReport` request:
  - dimensions `sessionCampaignName` and `sessionSource`, filtered to `BEGINS_WITH rz_`;
  - metrics `sessions` and `keyEvents`;
  - the last 90 complete days, ending yesterday.
- How report rows are handled:
  - rows that are not Ryzevo tags are dropped;
  - thresholding, sampling, the `(other)` row or a truncated table mark the result partial;
  - malformed metrics fail the read.
- A failed read keeps the last good result. The read is blocked and the stored results are deleted if any of these change during it:
  - the person loses access;
  - the connection is deactivated;
  - the property changes.
- Choosing another property also deletes the results.

**What people see.**
- Each accepted, tagged post shows "Visits to your site (Google Analytics)": sessions and key events for its tag and channel, with the period.
  - "No session seen" is shown when the read had no row for it.
  - "Waiting" is shown for a post published after the measured period.
  - A missing read is never shown as zero.
- "Growth coach: what we learned" adds visits per channel and the five posts that brought the most sessions.
- The monthly rule-based renewal moves a channel to the front by visits only when all of these hold:
  - there is no engagement leader;
  - at least two channels have tagged posts;
  - the leading channel has two or more posts and more sessions than the next.
- The reason names the figure and says it is an observation, not proof of cause.
- The AI renewal gets the same per-channel facts.

**Honesty rules.** Counts are sessions that arrived through a tagged link (GA4 session source), not results caused by a post. Visits from people who copied the link elsewhere are counted on that post; untagged arrivals are not counted. No personal data is stored, only counts per tag and source.

**Storage.**
- `platform_social_publications.link_tag` is set when the approved text contained a tagged link.
- `platform_link_tracking` holds per-project settings, the read state, the lease and the stored period.
- `platform_link_results` holds counts per tag and source, replaced on every successful read.
